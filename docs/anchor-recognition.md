# 本机 MediaPipe 图像匹配

正式链路：GPS 获取附近参考图 → Worker 计算图像特征 → 余弦相似度与连续确认 → 请求关联内容 → 在当前 SLAM 会话内放置并锁定。相机图像留在设备，不上传到 Web 或 SAGE；管理端的匹配点、参考图、关联投放与地图识别方式保持原有接口。

匹配识别与混合模式都运行这条链路。混合模式还并行显示未关联识别目标的 GPS 投放；匹配命中、重扫和移动刷新只替换匹配内容，不清理 GPS 或活动内容。新地图默认混合，已有地图保留所选模式，完整发现规则见[拉取策略](fetch-trigger-strategy.md)。

## 运行方式

- 地图配置 `retrieval_mode: anchor` 使用本机图像匹配；`gps` 仍直接显示附近素材。进入前必须选择具体地图，配置失败可重试。
- 两种模式都从一开始使用一个 VisionKit v2 SLAM 会话。识别只读取像素，不等空间定位完成；命中后也不切换相机会话。需要放置内容时才等待有效的米制位姿。
- 模型沿用实验中固定的 MediaPipe MobileNet V3 Small float32/1，输出 1024 维 L2 归一化特征。**生产运行器是 CPU TFLite Worker，实验页仍保留 MediaPipe Tasks Vision SDK 作基线。**微信 Worker 没有 Canvas/wx API，无法原样搬入依赖 WebGL 输入的浏览器 SDK，因此直接执行同一模型并核对特征一致性。
- 固定 `@tensorflow/tfjs-tflite@0.0.1-alpha.10` 的无 SIMD、单线程解释器；只打包 CPU 运行器，不引入 TensorFlow.js 张量框架。构建适配把 Emscripten 动态函数生成改成闭包，并保留已验证的 WASM `memory.copy` 优化。模型权重、网络结构不变。
- 模型元数据为 224×224 RGB、mean=0、std=255，即 `RGB / 255`；不能套用其他 MobileNet 常见的 [-1,1] 归一化。参考图和相机都缩放整张图片至 224×224；透明参考图铺白。参考图短边至少 224 像素。
- WASM、模型三段和 Worker 均从小程序代码分包载入，无本机模型服务器、Google 下载域名或新增后端接口依赖。模型与运行器哈希、输入输出形状和分包路径由构建脚本写入 `lib/image-matcher/build-info.js`；每包小于 1.5 MiB，三段按顺序拼接后的模型哈希不变。
- Worker 的 `text-encoding` 保留 TFLite 使用的 UTF-8、UTF-16LE/BE 编解码，构建时省略无关的传统字符集索引表。该裁剪是上游支持的用法，见 [text-encoding 编码说明](https://github.com/inexorabletash/text-encoding#encodings)；不改变模型输入和推理数值。

## 代码结构

| 位置 | 职责 |
| --- | --- |
| `lib/image-matcher/spec.js` | 从 `build-info.js` 派生输入边长、RGBA 字节数、特征维度和分包路径；其他代码不写死 224 / 1024 / 包路径 |
| `lib/image-matcher/policy.js` | 纯函数：相似度、匹配判断、连续确认、取帧间隔、像素有效性、GPS 移动与观看意图判断 |
| `lib/image-matcher/client.js` | 分包载入、Worker 生命周期、单请求通道与超时 |
| `lib/image-matcher/errors.js` | 错误码（`code`）；`message` 仍是面向用户的中文提示 |
| `workers/image-matcher/` | Worker 内推理；形状由初始化消息传入，错误回传相同的 `code` |
| `components/xr-start/matching/index.js` | 识别流程编排：候选 → 参考特征 → 相机匹配 → 内容 → 放置 |
| `matching/state.js` | 识别阶段（`PHASES`）、合法切换表，以及每轮扫描字段的唯一初始值 |
| `matching/candidates.js` / `location.js` / `reference-cache.js` | 接口请求体与响应校验、识别定位、按版本复用的参考特征 LRU |

`_cancelRetrieval` 用 `scanState()` 整体恢复每轮字段，`buildInitialState()` 也从同一处初始化，新增字段不会只在一侧生效。阶段切换经过 `_setMatchPhase`，不合法的切换记录 `非法识别状态切换` 错误日志。场景素材清理 `_clearRemoteAssets` 属于 `assets/index.js`。

## 调度与释放

参数统一在 `components/xr-start/matching/config.js`：

- 默认每秒取一帧；依据上一帧端到端耗时自动延长至 1–3 秒（耗时的 4 倍）。目标明确领先期间（见下文快速确认的 0.45 / 0.2）间隔下限降到 0.5 秒、取耗时的 2 倍，确认或领先丢失后恢复；边缘领先不加速。整个客户端只允许一项 Worker 请求在途，忙时跳过相机帧，不排队。
- `VKFrame.getCameraBuffer(边长, 边长)`（边长来自 `spec.INPUT_EDGE`，当前 224）和自有 RGBA 副本在原生帧回调中同步完成；帧回调结束后再发送约 196 KiB 的像素给 Worker。预处理归一化和模型推理在 Worker 内；主线程用同一份相机特征计算全部候选的向量内积，每张相机画面只运行一次模型。
- 黑暗/空白画面不参与确认并清空累积证据；超过 2.5 秒返回的帧结果同样丢弃并清空。
- 模糊帧不送推理：取帧时用 224×224 像素的绿色通道平均梯度估计清晰度，低于本轮扫描近期平均值的一半（`blurSharpnessRatio`）视为模糊，0.15 秒后重取，累积证据保留；连续最多重试 3 次，之后照常推理。近期平均值跟随每一帧（含被跳过的帧），所以持续低纹理的画面不会一直被跳过。只做相对比较，没有绝对清晰度门槛；0.5 的比例尚未在手机上校准。
- 每个目标按时间加权移动平均累积分数（`scoreSmoothingMs` 1.5 秒，每秒一帧时新帧约占一半权重；首帧直接取原始分数，相邻帧超过 4.5 秒重新开始）。阈值与领先差作用于平滑后的分数：平滑分数至少 0.4，领先第二候选至少 0.08。只有单帧本身也满足阈值与领先差、且指向同一领先目标的帧才计一次确认；单帧偏弱但平滑领先仍成立时暂停计数而不清零，平滑领先丢失或领先目标改变时从零开始。
- 分数突然上升时不做平均：某个目标的本帧分数比它的平滑分数高出至少 0.25（`scoreJump`）时，平滑分数直接取本帧分数。镜头转向目标是一次突变而不是噪声，继续平均会让平滑分数落后两三帧；分数下降始终逐步衰减，所以刚离开的目标仍压着领先差，判断偏保守。
- 2026-11-16 iPhone 15 Pro 实景两次扫描（同一地点、7 个目标，样本很小）：未对准目标的 15 帧最高原始分 0.32，对准目标的 6 帧为 0.49–0.66；对准瞬间原始分上跳 0.33 / 0.35，未对准时单帧上跳最大 0.14。没有突变规则时，两次都因平滑落后（原始 0.57 时平滑 0.40）走满 3 次、首次领先到确认 2.0 秒，明确领先与加速取帧都未触发；用同一批帧重放，0.25 的突变门槛使两次都在第 2 个明确帧确认，未对准的 13 帧不产生领先。0.15 的门槛在合成模拟里把无目标误命中从 35% 提到 47%，0.25 为 38%。预取使确认后 6 毫秒内容就绪（预取请求本身 1093 / 99 毫秒）。模糊跳过触发 1 次（清晰度比 0.39，代价 155 毫秒），无法区分是运动模糊还是转向纹理较少的目标；正常画面的清晰度在 8–40 之间波动。
- 两条确认路径，先满足的生效，`确认命中` 的 `via` 记录是哪一条：
  - 快速（`fast`）：连续 2 帧（`strongObservations`）各自单独明确领先，即本帧原始分数至少 0.45（`strongScore`）、原始领先差至少 0.2（`strongMargin`，附近只有一个目标时不要求），且指向当前平滑领先的目标；两帧相隔至少 0.5 秒。中间任何一帧不满足，连续计数归零。用原始分数判断是因为平滑分数会落后于刚进入画面的目标；配合 0.5 秒取帧，首次明确领先到确认约 0.5 秒。
  - 慢速（`slow`）：上面的平滑规则，累计 3 次、跨度至少 1.8 秒，约 2 秒，负责分数在门槛附近的目标。
  - 面板诊断显示 `确认 n/2` 或 `n/3`；`匹配结果` 的 `strong` 表示本帧是否明确领先，`observations` 是当前显示的进度，`slowObservations` 是慢速路径的累计次数。
  - 0.45 / 0.2 取自 2026-11-16 两轮 iPhone 15 Pro 实景日志共 5 次扫描、40 帧（同一地点、7 个目标）：对准目标的 17 帧原始分 0.43–0.66、领先差 0.23–0.42；其余 23 帧原始分不超过 0.40、领先差不超过 0.18，没有一帧单独达到快速门槛。两侧余量都只有约 0.03–0.05，换地点或目标更相似时需要重新核对。此前快速路径按平滑分数 0.55 / 0.15 判断，5 次扫描中一次都没有提前确认：对准目标时原始分多在 0.48–0.56，平滑分数到第 3 帧才过线。按原始帧判断后，同一批帧重放 5 次都在第 2 个明确帧确认（每秒一帧的日志上各早 1 帧）。合成模拟中最苛刻的无目标场景误命中由 38% 升到 46%，该场景的非目标均值 0.38、波动 0.1，比实测非目标帧（最高 0.40）严苛得多。
- 平滑的作用：走近目标时分数逐步上升会持续累积，单帧噪声（目标偏低或竞争目标突然偏高）只把排名拉动一部分。2026-11-16 合成分数序列模拟（`σ≈0.07–0.10` 高斯噪声、三个目标、12 帧，非真实相机数据）中，稳定目标 12 帧内确认率 83%→94%，走近目标 97%→99.5%，相似目标误命中 1.2%→0.4%，无目标噪声误命中 14.8%→12.4%；15% 模糊帧场景无改善（83%→82.5%），因为模糊帧会同时压低所有目标、领先差消失。曾试过平滑领先丢失后仍保留 4.5 秒，模糊场景升至 95%，但无目标误命中翻倍至 29%，未采用。
- 缩短确认的取舍（同一合成模拟，12 秒窗口）：所有目标统一改为 2 次时，无目标误命中从 13% 升到 44–48%，未采用；只对明确领先改为 2 次，明确目标的确认时间从 2.1 秒降到 1.2 秒，稳定目标 4.4→3.8 秒，无目标误命中 12.8%→13.4%，相似目标误命中 0.3%→0.6%。
- 加速取帧的取舍（2026-11-16，同一合成模拟改为相邻帧噪声相关、相关时间 1 秒；绝对值比上面的独立噪声模拟高，只比较相对变化）：任何领先都加速时，无目标误命中 34%→51%，因为边缘领先在同样两秒内更容易凑够 3 次，未采用；只对明确领先加速，明确目标确认 1.4→1.0 秒，无目标误命中 34%→35%，相似目标误命中 4.1%→4.7%。模糊帧若能检出 80%，有模糊帧场景的确认率 86%→95%。明确领先期间 Worker 负载加倍，对渲染帧率和发热的影响尚未在手机上测量。
- **0.4（2026-11-10 由 0.5 下调）是用于验证命中后空间内容显示的试验阈值，真实建筑的误匹配率和阈值仍需实景校准；通用特征相似不等于精确建筑定位。**
- 寻找目标时增加独立的低阈值提示：本帧最高原始相似度达到 `hintScore`（0.30）时，底部识别面板的内沿边框柔和闪烁，提示“画面中可能有目标”；降到 `hintReleaseScore`（0.26）以下结束，使用不同开关门槛减少抖动。该提示不要求领先差，不改变正式命中阈值、连续确认、预取或取帧频率，也不能指出画面中的具体物体位置。重新识别时，当前已显示目标占本帧第一名则不提示。黑暗、过期结果立即关闭，模糊重试可暂时保留，但超过 `hintStaleMs`（4.5 秒）没有新鲜有效结果会自动关闭；确认命中、停止扫描、失败、重扫、模式切换及隐藏退出都清理提示。0.30 / 0.26 是待真机校准的提示门槛，可能对相似背景产生提示，不等同于识别成功。
- 一个目标可有 1–5 张识别图（不同角度或光线）。每张图都计算特征，单帧目标得分取其中最高的一张；同一目标的多张图不互相计算领先差，只与其他目标比较。走近过程中最佳匹配的图可以从远景切到近景，证据按目标而非单张图累积。不采用多图求和或 top-k 平均：求和会偏向图多的目标，平均会惩罚角度差异大的图组。任意一张图无法准备时，该目标视为未就绪。
- 沿用旧 SAGE 的全候选比较思路：一次获取当前范围内全部目标，逐张准备特征后，每次相机推理与全部参考特征比较，不分批轮换。任何竞争参考图未就绪时暂不接受匹配，避免遗漏第二名造成误命中；重扫时只重试尚未缓存的参考特征。
- 每 5 秒检查 GPS，优先读取已有持续定位流；相对上次候选查询位置的距离达到 `max(20 米, 两次定位 accuracy 之和)` 才刷新附近目标。定位检查、单次定位等待不暂停正在进行的图像匹配。位置稳定时不重复拉取候选，空候选也保持到移动或手动重扫；后台修改的目标可通过重扫刷新。
- 参考特征按团队/地图作用域、目标 ID 与 `reference_version` 缓存在内存，采用最多 200 个目标的 LRU（每张图约 4 KiB 特征，单个目标最多 5 张）。`reference_version` 覆盖全部识别图及顺序，增删任意一张都会让该目标整体重新计算。移动、命中和手动重扫保留缓存；新目标或版本变化才下载并计算。新区域之外的旧向量保留至 LRU 淘汰，走回时可以复用；不把相机每帧结果作为可复用参考特征。
- 每次位置明显变化会取消旧推理和内容请求、重置连续确认并刷新候选；已锁定的识别内容也会清理，活动留言独立保留并按活动范围刷新，开始新区域的识别，SLAM 会话继续复用。参考图准备与相机推理串行，不抢同一个 Worker。
- 初始化总时限 30 秒，单次推理 10 秒；超时或 Worker 被系统终止会关闭进程并给出重新扫描入口，不回退主线程同步推理。
- 目标首次领先时即预取其关联内容（`预取内容` 日志），确认后直接使用；预取失败时确认后重新请求，未确认的预取结果随本轮扫描丢弃、不显示。每轮扫描最多预取 2 个目标（`maxContentPrefetches`），与候选接口共用每设备每分钟 60 次的限额。`内容就绪` 日志的 `prefetched` 与 `elapsedMs` 记录确认到内容可用的等待。
- 命中后立即停止 Worker。内容读取完成且当前 SLAM 位姿有效时才放置；内容在世界坐标中锁定，目标离开镜头不清场。特征不提供三维位姿，因此不会自动贴合建筑表面。
- 内容锁定后按 SLAM 相机位姿估计用户是否离开（`matching/config.js` 的 `away*` / `return*`，判定函数 `policy.contentView` / `attention`）：以锁定相机水平朝向前方 2 米为固定观看参考点，水平朝向偏离该点超过 45°、手机俯仰超过 60°（放下或朝天）、或距该点超过 8 米，持续 0.6 秒算离开；回到 30° / 6 米以内且俯仰不超过 60°，持续 1.5 秒算回来。距参考点 1 米内改为与锁定朝向比较，近距离原地转身仍可触发。该参考点在本次锁定期间不随节点位置变化，避免迟到素材重新朝向用户或 Scene 自定义原点过远影响判断；它是观看方向的近似，不是识别物体的三维定位。位姿无效时不采样；丢失跟踪立即清除待确认计时，保留已确认的离开状态；采样间隔超过 1 秒也重新计时。
- 离开只是在后台恢复取帧（阶段 `reacquiring`，重新启动 Worker、复用本轮候选和缓存特征，不请求候选接口），已显示的内容保留；确认到另一个目标后读取内容，待内容列表就绪且 SLAM 位姿有效才清理旧内容并开始放置新内容（`切换目标` 日志；模型、媒体资源仍按原队列异步加载）。当前目标再次领先不切换、不预取、不加速；看回原观看方向并满足返回延时后停止 Worker，回到 `locked`。附近只有一个目标时不启动；后台 Worker 或替换内容请求失败不影响已显示内容，仍在离开状态时 10 秒后再试。GPS 移动与手动重扫的清理规则不变。日志 `离开内容` / `回到内容` 带 `offsetDeg`、`pitchDeg`、`distanceMeters`（相对量，不含坐标）。
- 以上角度、距离和时间均未在手机上校准；两个目标在视线上相距不到 45° 时，仅靠转身不会触发，需要走动或手动重扫。
- 重新扫描清理识别内容与旧 Worker，保留独立活动留言，重新获取候选元数据并复用同版本的向量缓存和当前 SLAM 会话。隐藏/退出/模式切换取消全部异步任务，释放向量缓存并销毁 Worker；页面恢复先读新地图配置，再开始新会话。旧下载、旧推理、旧内容响应不能覆盖新扫描。
- 参考图片临时文件解码后即删除，Canvas 随即释放；相机帧不编码 JPEG，不存盘，不写 Storage。

## 接口与访问范围

统一经过 `utils/backend.ts`，地址规则见[本地开发](local-development.md)。完整服务端契约见 Web 仓库 `docs/miniapp-api.md`。

| 接口 | 用途 |
| --- | --- |
| POST `/api/miniapp/anchors/candidates` | workspace_id、latitude、longitude、accuracy、gps_timestamp、coordinate_system=wgs84；返回 id、name、image_urls（全部识别图，1–5 张）、image_url（第一张，兼容旧客户端；缺少 image_urls 时客户端只用它）、reference_version、distance_meters |
| POST `/api/miniapp/anchors/content` | 同样 GPS 字段，加 anchor_id、reference_version；返回 anchor 与 assets |
| POST `/api/miniapp/anchors/recognize` | 旧图片上传入口返回 410，本客户端不调用 |

优先用 10 秒内持续 GPS，否则用 5 秒内单次缓存或重新定位。服务端仍校验地图、范围、状态与参考图版本；范围最多 200 米、最多 200 个候选，暂停/移除目标返回 404，参考图改变返回 409。内容失败保持错误，等待用户重新扫描。附近无目标时，移动超过上述 GPS 阈值或手动重扫后重新查询。

匿名设备限流沿用 `anchorMatchClientId` 与 `X-Client-Id`；客户端识别结果不作为打卡凭证。域名配置仍只需原有后端 request、参考图 downloadFile 白名单；本次修改不会停止已部署的 SAGE 服务或取消计费。

## 页面状态接口

`xr-start` 的 `recognitionstatus` 事件为 `{ mode, message, diagnostic, phase, locked }`：`message` 是底部识别面板的业务提示；`diagnostic` 携带准备数量、确认次数或原始错误等技术信息，无额外诊断时为空；`phase` 为当前识别阶段，`locked` 标记内容锁定。`matchprogress` 继续使用 `{ mode, text }`，提供匹配进度及数值。独立的 `recognitionhint` 事件为 `{ mode, active }`，仅在低阈值提示开关变化时发出，不解析诊断字符串来驱动 UI。

`pages/ar/modules/recognition.ts` 只接收当前模式的事件，将业务提示交给 `ar-recognition-panel`，通过注册表 `publishDebug()` 将诊断和匹配数据交给顶部单行调试栏。重新扫描由面板发送 `{ moduleId: "recognition", action: "rescan" }`，经注册动作调用 XR。slot 装配、动作包与状态保留规则见 [AR 页面 Slots 与功能导航](ar-bottom-stack.md)。

低阈值提示通过 `recognitionHintActive` 传给识别面板，仅面板内沿边框以 1.6 秒周期明暗变化；navbar 图标、标签及按钮不增加动效，避免暗示用户点击。边框使用内描边，不改变布局，也不拦截触摸；文字保持稳定。系统支持 `prefers-reduced-motion` 时改为静态内描边。识别面板收起或切到其他业务时不绘制该效果，也不自动切换或展开面板。页面隐藏、配置切换及重扫同时清理页面状态，迟到事件不能在已隐藏或退出页面重新点亮。

自动重新识别的专项真机验收：同一附近候选集内识别 A，原地转向 B（包括走到观看参考点附近再转身），确认 A 保留到 B 的内容列表与位姿就绪才切换；短暂转头不应启动，转回原观看方向后应停止后台扫描；放下手机、向后走远、短暂丢失跟踪后恢复分别验证延时；慢资源和自定义远观看位置 Scene 不应移动观看基准；断网或 Worker 失败应保留 A。以下本地回归只覆盖 Node / 微信 API 替身，不能替代手机阈值和 Worker 重启耗时校准。

### 自动扫描诊断

进入识别地图后由相机帧自动启动，无需点重新扫描。`附近目标` 只代表候选接口返回，不能证明相机已经完成推理。启动链路依次记录 `识别启动`、`识别模型就绪`、`参考图就绪`、`扫描开始`；页面准备好后显示“自动识别中”。

实景校准期间 `config.frameLogs` 为 true：每个采样帧输出一行 `匹配结果`（含被跳过的黑暗帧、模糊帧和过期结果），校准完成后改回 false，只在首个结果、原因变化和确认进度变化时输出。每行带 `tMs`（本轮诊断开始后的毫秒数，控制台行本身没有时间）、`frame`（推理帧序号）和 `scores`：本帧原始分最高的最多 5 个目标（`frameLogTargets`），每个含 `raw`（本帧分数）、`smooth`（平滑分数）、`image`（本帧最匹配的识别图序号，从 0 起，对应管理端的图片顺序）。`sharpness` / `sharpnessBaseline` 是本帧清晰度和此前的近期平均值，模糊帧另带 `sharpnessRatio`。`leadMs` 是当前领先目标已领先的时间。`扫描摘要` 的 `lastResult` 不重复 `scores`。

`扫描开始` 记录 `device`（机型、系统、微信与基础库版本）、`targets`（每个目标的 ID、名称、识别图数量、取整的距离）和本轮全部判定参数。`确认命中` 记录 `strong`、`observations`、`frames`、`leadMs`（首次领先到确认）与 `scanMs`（扫描开始到确认）；`预取内容` / `预取完成` / `预取失败` 记录预取发起的帧和耗时；`内容已锁定` 的 `scanMs` 是扫描开始到内容显示的总时间。目标名称只出现在本机控制台的 info 日志，不随错误上报。

未命中也记录 `匹配结果`，包含 `topScore` / `minimumScore`、与第二候选的 `margin`、确认次数、取帧和推理耗时。`reason` 为 `score_below_threshold`（低于阈值）、`ambiguous_targets`（两个目标太相似）、`invalid_pixels`（画面缺少有效细节）、`blurred_frame`（画面模糊，带 `sharpness` / `sharpnessBaseline`）、`stale_result`（返回过晚）、`confirming` 或 `confirmed`。相同判断不逐帧刷日志，最新数值合并进摘要；页面状态未变时不重复触发更新。`扫描开始` 记录本轮 `cacheHits` / `cacheMisses`；`移动后刷新目标` 只记录移动距离和刷新门槛，不记录坐标。

扫描期间每 3 秒输出一次 `扫描摘要`，不依赖相机或 Worker 回调。失败日志带 `code`（如 `TIMEOUT`、`WORKER_KILLED`、`INFERENCE_FAILED`），按错误码区分超时、进程退出与推理失败，不依赖提示文案。`stage` / `stageMs` 指出等待相机、定位、候选接口、Worker 初始化、参考图或扫描的阶段；`cameraFrames` / `captured` / `inferred` 区分相机帧到达、采样与推理完成，`blurredFrames` 统计因模糊跳过的采样，`workerBusy` / `inFlightMs` 区分等待结果，`lastResult` 保留最近一次判断。隐藏、退出、命中或错误后取消摘要定时器。真机未命中时先比较这些字段，再决定修复取帧、模型初始化或校准阈值，不凭候选日志推断扫描没有启动。

依据（2026-11-09 核对）：[微信 Worker](https://developers.weixin.qq.com/miniprogram/dev/framework/workers.html)、[WXWebAssembly](https://developers.weixin.qq.com/miniprogram/dev/framework/performance/wasm.html)、[MediaPipe Image Embedder](https://ai.google.dev/edge/mediapipe/solutions/vision/image_embedder)、[TFLite Web 运行器](https://github.com/tensorflow/tfjs/tree/master/tfjs-tflite)、[模型元数据规范](https://github.com/tensorflow/tflite-support/blob/master/tensorflow_lite_support/metadata/metadata_schema.fbs)。

### Worker 真机结果（2026-11-09）

同一台 iPhone 15 Pro / iOS 26.6.2 / 微信 8.0.80 / 基础库 3.17.6，用户确认「后台识别验证完成」。两张同图 SDK/Worker 特征余弦相似度为 **0.999999999997 / 0.999999999998**；不同图为 0.300219。12 次合成图 Worker 推理 **149–156ms，P50 151ms**；主线程 16ms 定时器回调 135 次，最大间隔 **51ms**。证据：[完整手机报告](benchmarks/image-match-worker-iphone15pro-2026-11-09.json)。

该报告验证数值和 Worker 推理期间的 JS 响应，没有采集真实相机或渲染 FPS。51ms 不是零卡顿承诺；149–156ms 不能当作相机端到端耗时，也不能直接与先前 SDK 的 480×640 相机实验做百分比性能承诺。真实地点正负样本、拍摄方向、识别阈值和完整 AR 媒体流畅度仍需现场验收。
